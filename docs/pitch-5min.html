Introduction & Problem Statement

0:45 → 1:25
Main spoken script

We are Radiants. Six of us. And that gap is exactly Problem Statement 26011.

Let me explain what it actually means. India already has ULPIN — a unique number for every land parcel. But it works only on the ground plane. X and Y. A flat map.

A city is not flat. At one single location you can have flats above, parking below, and a metro tunnel deeper still.

So the problem statement asks us to add the third dimension — Z. Height and depth. Simple words mein — same location, but different levels.

And it has to happen automatically, because doing this by hand for every building in India is simply not possible.

Person 3

The Problem & What Is Required

1:25 → 2:20
Main spoken script

Let me show you why. This is a section through one single plot.

A metro tunnel, fifteen metres below. A water main above it. Two levels of parking. Shops at ground level. Eleven floors of flats. Air rights on top.

Fourteen separate legal spaces. Four different authorities. Different owners. And every one of them sits at the same X-Y coordinate.

Aur 2D record sirf ek hi line dekh sakta hai — the ground.

This creates three real problems. Disputes have no geometry to settle them. A builder digging a basement cannot see what runs below. And if someone adds an extra floor, the file will never know.

So the requirement is clear. Give every meaningful space its own 3D identity. Extract it automatically from survey data. And validate it for errors.

Now — what makes this different.

Every identifier carries a check character. If a clerk mistypes even one digit, the number is rejected offline, before it touches any database. We tested all 910 possible single-character errors. Every one caught.

1 · Why 2D is insufficient

1.1The apartment flat★ Best
Situation
A twenty-storey building. Flat 302 and flat 1502.
What happens
Both flats sit on exactly the same building footprint.
2D fails
On a flat map they are the same polygon — the record cannot separate them.
3D solves
Adding the floor level and floor height makes each one a distinct volume with its own identifier.
“Flat 302 and flat 1502 have the same footprint, but they are obviously not the same property. Yahi 2D record ki limitation hai.”
1.2Multi-level parking
Situation
A mall with parking on three basement levels.
What happens
Bay B2-114 is sold to one owner, B3-114 to another.
2D fails
Both are “parking” on the same plot. The record has one row.
3D solves
Each bay becomes a volume at a known depth, separately owned and searchable.
“Your parking ticket says which level. Your property record does not.”
1.3Metro tunnel under a house
Situation
A metro line runs fifteen metres beneath a residential plot.
What happens
The metro authority holds a right to that depth; the owner holds the surface.
2D fails
Both claims map to the identical polygon, so the map shows a conflict that is not one.
3D solves
Different Z ranges mean two clean, separate records that never overlap.
“The house and the tunnel are at the same place on the map — and fifteen metres apart in reality.”
1.4Shop below, home above
Situation
A typical mixed-use street building: shop at ground, family upstairs.
What happens
Commercial and residential use, different owners, one plot.
2D fails
The plot must be labelled with a single land use, so one of the two is misrecorded.
3D solves
Use is recorded per volume, so ground floor is commercial and the floors above are residential.
“One plot, two land uses, stacked. A flat map has to pick one and get the other wrong.”
1.5Flyover over a road
Situation
An elevated corridor passes above an existing municipal road.
What happens
Two authorities operate two assets stacked vertically.
2D fails
Overlapping polygons look like an encroachment when nothing is wrong.
3D solves
The elevated structure sits in an air-rights band above the road surface.
“On a 2D map, a flyover looks like it is encroaching on the road below it.”

How to explain our uniqueness

pick one

Never say these

“We are the first in the world.” · “Nobody has done 3D cadastre.” Both are false — 3D cadastre is an established research field with pilots in the Netherlands, Singapore and Queensland. Claiming otherwise loses the judge instantly if even one of them knows the field.

V1The combination version★ Best
“3D cadastre is a known research area. What we have not found combined in one working system is this: an identifier built as a backward-compatible extension of India's existing ULPIN, fully automated extraction with no manual digitisation, property and infrastructure validated against each other, and a pipeline that reports its own measured accuracy on every run.”
Why best
Honest, specific, and every clause is demonstrable on the laptop.
V2The deployability version
“Most 3D cadastre work assumes rich survey data. We built two doors into the same system — a drone path for accuracy, and a 2D plan path that a municipal office can run today with files they already hold, offline, on a normal laptop.”
Use when
The panel leans administrative or policy rather than technical.
V3The evidence version
“Our difference is that we do not ask to be believed. Every stage scores itself against known ground truth, every boundary records whether it was surveyed or inferred, and 158 tests run in thirty seconds. It is a record you can audit, not a visualisation.”
Use when
A technical judge is probing rigour, or after a hard question.
V4The one-sentence version
“We did not build a 3D map. We built a land record that happens to be three-dimensional — with identity, ownership, provenance and validation.”
Use when
Time is short, or someone calls it “just a 3D viewer”.

What algorithms?SMRF ground filtering (Pingel et al., ISPRS 2013); PCA eigenvalue features for roof-vs-tree; DBSCAN for building instances; alpha shapes for outlines; RANSAC for roof planes; autocorrelation on the facade for floor detection.
Where is the deep learning?“We chose interpretable models because the output has legal consequences. A surveyor must be able to audit why a boundary was drawn. We built the interface a trained model plugs into and documented it.”
Your data is synthetic.“Synthetic so that ground truth exists — otherwise accuracy is an opinion, not a number. The pipeline reads real LAS/LAZ files today.”
Tech stack?Python 3.12, FastAPI, Shapely, NumPy, SciPy, laspy, rasterio. Viewer is hand-written WebGL2 — no library, works offline. 158 tests.
Does it scale to a city?“Extraction is tiled and near-linear. Storage is currently a JSON document, which is right for hundreds of objects; PostGIS drops into the same interface for city scale. That is scoped work, not an unknown.”
Legal basis for a 3D ULPIN?“A volumetric extension does not yet have a statutory framework, and we will not claim otherwise. We built it as an extension — the first three fields are the existing LGD codes, and imported 2D boundaries keep their authority.”
Spoken to a department?Do not bluff. “Not yet. We grounded the design in LGD codes, the existing ULPIN structure, DILRMP and SVAMITVA. A one-ward pilot with a ULB is our next step.”
Cost to deploy?“No licence cost — every dependency is open source. No cloud, no API keys. The real cost is the drone survey, which SVAMITVA already funds.”
